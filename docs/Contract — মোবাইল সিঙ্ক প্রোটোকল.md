# চুক্তি — মোবাইল সিঙ্ক প্রোটোকল

**তারিখ:** ২ সেপ্টেম্বর ২০২৬
**দুই পাশ:** `abos/mobile/lib/core/` (Dart) ↔ `abos/app/Core/Engines/Sync/` (PHP)

এই কাগজটা **দুই পাশের মাঝের চুক্তি**। যেকোনো এক পাশ বদলালে অন্য পাশ
নীরবে ভাঙে — কোনো কম্পাইলার এই সীমানাটা পাহারা দেয় না, তাই কাগজটাই
একমাত্র পাহারা।

---

## মালিকের তিনটা সিদ্ধান্ত, যেগুলোর উপর পুরোটা দাঁড়ানো

**১ · নেট না থাকলে শুধু অর্ডার।** চালান, বিল, আদায়, POS — একটাও নয়।

কারণটা সুবিধার নয়, হিসাবের সততার। অফলাইনে চারটা জিনিস অন্ধ:

| | অফলাইনে যা জানা যায় না | না জানলে যা ঘটে |
|---|---|---|
| নম্বর | সিরিজের পরের নম্বর | দুইটা ফোন একই নম্বর দিত |
| মজুদ | তাকে কী আছে | দুইজন একই শেষ কার্টনটা বেচতেন |
| ক্রেডিট সীমা | দোকানের বকেয়া | যাঁর টাকা আটকে তাঁকেই আরও মাল |
| দাম | আজকের দর | পুরনো দামে বিল |

**অর্ডার এই চারটার একটাতেও হাত দেয় না** — ওটা প্রতিশ্রুতি, দাখিলা নয়।
চারটাই যাচাই হয় সিঙ্কের মুহূর্তে, সার্ভারে।

**২ · অর্ডারের নম্বর বসে সিঙ্কের সময়**, সার্ভারে। সেলসম্যান অফলাইনে
দোকানদারকে নম্বর বলতে পারবেন না — **পর্দায় সেটা সৎভাবে দেখাতে হবে**,
একটা ফাঁকা ঘর নয়।

*(বিকল্প ছিল ফোনে আগে থেকে নম্বর বরাদ্দ করা। অব্যবহৃতগুলো সিরিজে ফাঁক
রেখে যেত, আর অডিটে প্রতিটা ফাঁক ব্যাখ্যা করতে হয়।)*

**৩ · এক অ্যাপ সবার জন্য** — মালিক, কর্মী, ডিলার, সরবরাহকারী; যে যার
রোল অনুযায়ী।

⚠️ **তবে আজ কেবল কর্মীরা** — মালিকের সিদ্ধান্ত, ২ সেপ্টেম্বর ২০২৬:
*"এখন শুধু কর্মীরা — ডিলার পরে, আলাদা কাজ হিসেবে।"*

ডিলার একটা `Customer`, কর্মী নন। আজ তিনি API-তে **লগইনই করতে পারবেন না**,
আর সেটা তিন জায়গায় বাঁধা:

```
Customer মডেলে HasApiTokens   নেই — টোকেন ধরতেই পারে না
CredentialCheck খোঁজে         User — ডিলার ওই টেবিলে নেই
Auth/SyncController           abort 403 যদি User না হয়
```

সেদিন যা লাগবে, আর কেন কাজটা ছোট নয়: পোর্টাল-গার্ডে টোকেন, **আর
প্রতিটা হ্যান্ডলারে "শুধু নিজেরটা" ছাঁকনি**। দ্বিতীয়টাই আসল কাজ — এক
ডিলার অন্য ডিলারের বকেয়া বা গ্রাহক-তালিকা পেয়ে গেলে **প্রতিযোগীর
তালিকা প্রতিযোগীর হাতে**, আর একবার ফোনে নেমে গেলে ফেরত আনার উপায় নেই।

**নকশার জন্য:** ডিলারের পর্দা এখন বানাবেন না। রোল-ভিত্তিক মেনুর কাঠামোটা
রাখুন, কিন্তু আজকের একমাত্র দর্শক কর্মী।

**আজকের কর্মীর চাবি — মালিকের সিদ্ধান্ত, একই দিনে:**

> *"বিক্রয়কর্মী শুধু পণ্যের তালিকা দেখবেন, ক্রয়মূল্য দেখবেন না, স্টকও
> দেখতে পারবে না।"*

| | বিক্রয়কর্মী |
|---|---|
| গ্রাহক · বকেয়া · অর্ডার | ✅ |
| পণ্যের তালিকা ও **বিক্রয়**মূল্য | ✅ |
| **ক্রয়**মূল্য (`purchasePrice`) | ❌ ঘরটাই আসবে না |
| **মজুদ** (`StockOnHand`) | ❌ রেকর্ডই আসবে না |

⚠️ **মজুদের পর্দা তাঁর মেনুতে রাখবেন না** — সিঙ্কে কিছুই আসবে না, আর
ফাঁকা পর্দা দেখে তিনি ভাববেন ব্যবস্থাটা ভাঙা।

⚠️ **এর ফলে সিঙ্কের দরজাগুলোয় কোনো `can:` চাবি নেই**, আর সেটা ইচ্ছাকৃত।
ছাঁকনিটা এক ধাপ ভেতরে: প্রতিটা হ্যান্ডলার নিজের রেকর্ড ব্যবহারকারীর
অনুমতি ধরে ছাঁকে। **ফোনের পাঠানো `permissions` তালিকা কেবল মেনু সাজানোর
জন্য — কোনো নিরাপত্তা নয়।**

## ১ · ঢোকা

### `POST /auth/login` · throttle 10/মিনিট · টোকেন লাগে না

```jsonc
// পাঠায়
{
  "identifier": "sales@abos.test",   // নাম বা ইমেইল
  "password": "…",
  "code": "123456",                  // ঐচ্ছিক — MFA চালু থাকলে
  "deviceId": "…",                   // বাধ্যতামূলক, keystore থেকে
  "appVersion": "0.1.0",             // ঐচ্ছিক, সহায়তার জন্য
  "platform": "android"              // ঐচ্ছিক
}
```

```jsonc
// ২০০
{
  "accessToken": "…",                // প্রতিটা অনুরোধে, ৩০ মিনিট
  "refreshToken": "…",               // কেবল নবায়নে, ৩০ দিন
  "expiresInSeconds": 1800,
  "user": {
    "id": "…", "name": "…", "email": "…",
    "roles": ["salesman"],
    "permissions": ["customer.view", "…"]   // মেনুর জন্য, পাহারার জন্য নয়
  }
}
```

| অন্য উত্তর | মানে |
|---|---|
| **৪০৯** `{needsCode: true, codeWasWrong: bool}` | পাসওয়ার্ড ঠিক, দুই ধাপের কোড বাকি বা ভুল। **কোডের পর্দাটা খুলুন।** পতাকাটা দেখুন, বার্তার লেখা পড়ে নয় — অনুবাদ বদলায় |
| **৪২২** `{message, errors}` | পরিচয় বা পাসওয়ার্ড ভুল, বা নামটা তালাবদ্ধ। `message`-টা বাংলায়, সরাসরি দেখানোর মতো |
| **৪২৯** | throttle — খুব বেশি চেষ্টা |

⚠️ **ভুল কোড তালা বাড়ায়, কোড না দেওয়া বাড়ায় না।** দুই ধাপের ব্যবহারকারী
যেন নিজের কোড টাইপ করতে গিয়ে নিজেই তালাবদ্ধ না হন।

### `POST /auth/refresh` · `abilities:refresh`

`{ "deviceId": "…" }` → লগইনের মতো একই আকার।

⚠️ **টোকেন ঘোরে।** যে refresh টোকেন দিয়ে ডাকলেন সেটা **মরে যায়**; নতুন
জোড়াটা সংরক্ষণ করতেই হবে। পুরনোটা দ্বিতীয়বার ব্যবহার করলে ৪০১ — আর
সেটাই চুরির সংকেত।

### `POST /auth/logout` · `abilities:sync`

`{ "deviceId": "…" }` → কেবল **ওই ফোনের** দুইটা টোকেন বাতিল। অন্য ফোন
চলতে থাকে।

⚠️ ওয়াটারমার্ক **মুছে যায় না** — ওটা হ্যান্ডসেটের, ব্যক্তির নয়। পরের
লগইনে পুরো ক্যাটালগ আবার নামে না।

### ⚠️ দুইটা টোকেন, দুইটা আলাদা কাজ

`auth:sanctum` **যেকোনো** বৈধ টোকেন মেনে নেয় — refresh টোকেনও। তাই
সিঙ্কের দরজাগুলো `abilities:sync` চায় আর নবায়ন `abilities:refresh`।
**একটা দিয়ে অন্যটার কাজ হয় না**, আর সেটাই ছোট মেয়াদটাকে অর্থবহ করে।

## ২ · সিঙ্ক · সব দরজায় `abilities:sync` + `?deviceId=`

### `GET /sync/capabilities`

```json
[{"module": "customer", "entityType": "Customer"}, …]
```

**ফোন এখান থেকেই পরিকল্পনা বানায়, হাতে লেখা তালিকা থেকে নয়** — সার্ভারে
হ্যান্ডলার যোগ বা বাদ দিলে নতুন রিলিজ ছাড়াই কার্যকর হয়।

আজকের পাঁচটা:

| module | entityType | দিক | চাবি |
|---|---|---|---|
| `customer` | `Customer` | নামে | `customer.view` |
| `customer` | `CustomerDue` | নামে | `customer.view` |
| `inventory` | `Product` | নামে | `inventory.product.view` |
| `inventory` | `StockOnHand` | নামে | `inventory.stock.view` |
| `sales` | `SalesOrder` | **ওঠে ও নামে** | `sales.order.view` |

### `GET /sync/{module}/pull?deviceId=&limit=`

```jsonc
{
  "records": [
    {
      "entityType": "Customer",
      "entityId": "01a0…",              // public_id (UUID), ভেতরের id কখনো নয়
      "payloadJson": "{\"…\":\"…\"}",   // স্ট্রিং, নেস্টেড অবজেক্ট নয়
      "updatedAt": "2026-09-02T14:35:27+06:00"
    }
  ],
  "hasMore": false,
  "unreadable": []                      // যে ধরনগুলো সার্ভার পড়তে পারেনি
}
```

⚠️ **`since` প্যারামিটার নেই, আর সেটা ইচ্ছাকৃত।** ওয়াটারমার্ক সার্ভার
রাখে, তাই পরপর দুইবার ডাকলে **হুবহু একই ব্যাচ** ফেরে — আর সেটাই একটা
হারিয়ে যাওয়া উত্তরের পর আবার চেষ্টা করাকে নিরাপদ করে। ফোনের ঘড়ির উপরও
ভরসা করতে হয় না।

### `POST /sync/{module}/pull-complete?deviceId=`

⚠️ **কেবল তখনই ডাকুন যখন `hasMore == false` আর `unreadable` খালি।**

ওয়াটারমার্ক বসে **"এখন"**-এ, শেষ রেকর্ডের সময়ে নয়। তাই অসম্পূর্ণ ব্যাচের
পর ডাকলে ওই ব্যাচের কাটঅফ আর "এখন"-এর মাঝের প্রতিটা রেকর্ড **কোনোদিন না
পাঠিয়েই** সিঙ্ক-হয়েছে বলে চিহ্নিত হবে, আর আর কখনো আসবে না।

*নিয়মটা দুই পাশেই লেখা (`reference_sync.dart` আর `SyncService`), ইচ্ছে
করে — এক পাশ ভুল করলে অন্য পাশ ধরে ফেলে।*

### `POST /sync/{module}/push?deviceId=`

শরীরটা একটা **তালিকা**, বস্তু নয়:

```jsonc
[{
  "changeId": "local-1756800000000000-0",  // ফোনে তৈরি, প্রতিটা retry-তে একই
  "entityType": "SalesOrder",
  "entityId": null,                        // CREATE-এ খালি
  "operation": "CREATE",                   // বা UPDATE
  "payloadJson": "{…}",
  "clientVersion": 1
}]
```

```jsonc
{"outcomes": [{"changeId": "…", "status": "APPLIED", "entityId": "01a0…"}]}
```

| status | ফোন কী করবে |
|---|---|
| `APPLIED` | কিউ থেকে মুছে ফেলুন |
| `DUPLICATE` | কিউ থেকে মুছে ফেলুন — আগেই বসেছিল |
| `REJECTED` | **কারণসহ ধরে রাখুন**, সেলসম্যানকে দেখান |
| `CONFLICT` | একই — সার্ভারে নতুনতর বদল আছে |

⚠️ **`changeId` প্রতিটা চেষ্টায় একই হতে হবে।** দুইবার-বসা ঠেকানোর পুরো
ব্যবস্থাটা ওটার উপর দাঁড়ানো: `(device_id, change_id)`-তে ডাটাবেজ-স্তরের
unique। নতুন চাবি বানালে **একই অর্ডার দুইবার বসবে, আর কোনো যাচাই লাল
হবে না** — দুইটাই বৈধ, রেওয়ামিল মিলবে, শুধু বিক্রি দ্বিগুণ দেখাবে।

⚠️ **`REJECTED` মুছবেন না।** "০টা অপেক্ষমাণ" দেখে সেলসম্যান ধরে নেন সব
পৌঁছে গেছে — প্রত্যাখ্যাত সারি মুছে ফেলা মানে তাঁকে মিথ্যা বলা।

### `GET /sync/{module}/last-sync?deviceId=`

`{"lastSyncedAt": "…"|null}` — সহায়তার জন্য।

### `GET /sync/conflicts` · `POST /sync/conflicts/{id}/resolve`

⚠️ **এই দুইটায় আলাদা চাবি লাগে — `governance.audit.view`।** একটা দ্বন্দ্বের
সারিতে ফোনের রূপ **আর** সার্ভারের রূপ দুইটাই থাকে, অর্থাৎ ওটা দুই পাশের
যোগফলের চেয়ে বেশি গোপন। সাধারণ সেলসম্যান ৪০৩ পাবেন — **পর্দায় সারিটা
লুকান, নাহলে বোতামটা চাপলেই ভাঙা মনে হবে।**

## ৩ · যে নিয়মগুলো ভাঙলে নীরবে ভুল হবে

**ক · ভেতরের `id` কখনো তারে যায় না।** সব `public_id` (UUIDv7)। ক্রমিক
সংখ্যা গোনা যায় — "আমার আগে কতজন গ্রাহক ছিল"।

**খ · `payloadJson` স্ট্রিং হিসেবেই রাখুন**, ক্যাশে বা কিউতে অবজেক্ট
হিসেবে নয়। তাতে আজকের অ্যাপ যে ঘরগুলো চেনে না সেগুলোও অক্ষত থাকে, আর
পুরনো বিল্ড নতুন সার্ভারের উত্তরে ভাঙে না।

**গ · `outcomes` মেলান `changeId` ধরে, ক্রম ধরে নয়।**

**ঘ · শেষ এক মিনিট আবার আসবে — এটা বাগ নয়।** সার্ভার ওয়াটারমার্কের এক
মিনিট আগে থেকে পড়ে, কারণ একটা সারি লেখা হওয়ার আর **দৃশ্যমান হওয়ার**
মাঝে সময় লাগে (COMMIT)। ছুরির ধার ধরলে চলতি লেনদেনের সারিগুলো চিরতরে
হারাত। ক্যাশ `entityType:entityId` ধরে বসায়, তাই পুনরাবৃত্তি ক্ষতিহীন।

**ঙ · ⚠️ কিছু ঘর আসবেই না, আর সেটা ভুল নয়।** `purchasePrice` কেবল
`inventory.cost.view` থাকলে যায় — নাহলে **ঘরটাই থাকে না** (`null` বা
mask নয়)। পর্দায় ক্রয়মূল্যের ঘর রাখলে অনেকের কাছে ফাঁকা আসবে; নকশায়
সেটা ধরে রাখুন।

**চ · সাইন-আউটে `ReferenceCache.clearAll()`** — পরের মানুষটা অন্য
কোম্পানির হতে পারেন, আর পুরনো ক্যাটালগ তাঁর কাছে যাওয়া মানে টেন্যান্টের
দেয়ালে ফুটো।

## ৫ · অনুমোদন · `abilities:app`

**তারিখ:** ১৩ সেপ্টেম্বর ২০২৬ · মালিকের সিদ্ধান্তে অনুমোদিত, abos-10 ও
abos-33-এর মাঝে।

সিঙ্কের বাইরের প্রথম দরজা। ⚠️ **এটা সিঙ্ক নয়** — অফলাইনে কাজ করে না, কিউতে
বসে না, ওয়াটারমার্ক নেই। মালিক ডেস্কে নেই আর নথিগুলো দাঁড়িয়ে আছে — কেবল
সেই সমস্যাটার সমাধান, আর সেটা নেট থাকলেই।

*(কেন অফলাইনে নয়: একটা অনুমোদন মানে নথিটা এগিয়ে যায় — মজুদ সরে, টাকা
ছাড়ে। নেট ছাড়া সেটা করা মানে দুইজন একই নথি দুইবার অনুমোদন করে বসা।
মালিকের ১ নম্বর সিদ্ধান্তের সাথে এটা একই যুক্তি।)*

### `GET /approvals/pending?limit=&cursor=`

```jsonc
{
  "rows": [{
    "id": "01a0…",                  // public_id, ক্রমিক id কখনো নয় (§৩ ক)
    "documentType": "PurchaseBill",
    "documentNo": "PB-2609-0007",
    "action": "confirm",
    "amount": "125000.0000",        // ⚠️ স্ট্রিং, সংখ্যা নয় (§৩ ঙ-এর মতো)
    "currentLevel": 2,
    "requestedAt": "2026-09-13T09:40:00+06:00",
    "requesterName": "…",
    "summary": "…"
  }],
  "nextCursor": null
}
```

⚠️ **সার্ভার `pendingQueryFor()` ব্যবহার করে, `pendingFor()` নয়** — ওই
দুইটা ১২ সেপ্টেম্বর আলাদা করা হয়েছিল ঠিক এই কারণে যে গোনা আর দেখানো দুইটা
আলাদা কাজ, আর একটা সংখ্যা দেখানোর জন্য প্রতিটা সারি মেমরিতে তোলা হত।
মোবাইল ইনবক্স পাতা-ভাগ করে, তাই Builder-টাই দরকার।

⛔ **বেতন (`Payroll`) এই তালিকায় কখনো আসে না** — মালিকের সিদ্ধান্ত, ১৩
সেপ্টেম্বর। অঙ্ক ছাড়া সারি নয়, **সারিটাই নয়**; বেতন ডেস্কে অনুমোদন হয়।

কারণটা লিখে রাখা দরকার, কারণ এটা নীরবে ফিরে আসার মতো: §৪ বলে জনবল/বেতন
ফোনে যাবে না। কিন্তু বেতন **অনুমোদনযোগ্য** নথি, তাই সরলভাবে বানানো একটা
`/approvals/pending` ওই সিদ্ধান্তটা **পিছনের দরজা দিয়ে** ভেঙে দিত — আর
কেউ ধরত না, কারণ এন্ডপয়েন্টটার নাম "approvals", "payroll" নয়।

⚠️ **ছাঁকনিটা সার্ভারে, ক্যোয়ারিতে** — পর্দায় নয়। আর যাচাইটা **দুই দিক
থেকে**: একটা Payroll অনুমোদন সত্যিই বসিয়ে দেখতে হবে সেটা আসেনি, **আর
পাশে একটা অ-Payroll সারি যে এসেছে**। কেবল "তালিকা খালি" দেখে পাস করলে
সবকিছু-ছাঁকা একটা ক্যোয়ারিও সবুজ হত।

### `POST /approvals/{approval}/approve`

```jsonc
{ "remarks": "…" }     // ঐচ্ছিক
```

### `POST /approvals/{approval}/reject`

```jsonc
{ "remarks": "…" }     // ⚠️ বাধ্যতামূলক
```

⚠️ **কারণ ছাড়া প্রত্যাখ্যান হয় না**, আর নিয়মটা দুই পাশেই — `ApprovalEngine::reject()`-এর সই `string $remarks` (nullable নয়), আর অ্যাপের পর্দাতেও ঘরটা খালি রাখলে বোতাম নিষ্ক্রিয়। এক পাশে নিয়ম থাকলে অন্য পাশ একদিন অন্য কথা বলত।

### যে নিয়মগুলো ভাঙলে নীরবে ভুল হবে

**ক · `canDecide()` সার্ভারেই পাহারা দেয়।** ফোনের `permissions` তালিকা
কেবল মেনু সাজানোর জন্য — §০-এর শেষ সতর্কতাটাই এখানেও।

**খ · ৪০৩ মানে "আপনি নন", ৪০৯ মানে "আর নেই"।** একজন অনুমোদন করার আগেই
অন্যজন করে ফেলতে পারেন; পর্দায় সেটা ভুল নয়, ঘটনা — সারিটা তালিকা থেকে
সরে যাবে, লাল বার্তা নয়।

**গ · `amount` স্ট্রিং হিসেবেই পড়তে হবে।** `decimal:4` ⇒ `"125000.0000"`।
১২ সেপ্টেম্বর `salePrice` এই এক কারণেই পর্দায় কোনোদিন আঁকেনি: `as num?`
ভুল কী-তে `null` দেয়, আর `null` কিছুই আঁকে না।

**ঘ · তালিকা খালি হওয়া স্বাভাবিক।** "কিছু অপেক্ষা করছে না" একটা ভালো
খবর, ত্রুটির পর্দা নয়।

## ৬ · সংস্করণ পরীক্ষা · টোকেন লাগে না

**তারিখ:** ১৩ সেপ্টেম্বর ২০২৬ · মালিকের সিদ্ধান্ত: আগে সরাসরি APK, কাজ
প্রমাণিত হলে Play Store।

সরাসরি APK-তে Play Store-এর মতো আপনাআপনি কিছু হয় না। তাই ফোন নিজেই
জিজ্ঞেস করে নেয় সে পুরনো কিনা।

⚠️ **এই একটাই দরজা যেখানে টোকেন লাগে না**, আর কারণটা আছে: একটা পুরনো বিল্ড
লগইনই করতে না পারলে ঠিক তখনই তাকে বলা দরকার সে পুরনো। auth-এর ভেতরে রাখলে
যে অবস্থায় বার্তাটা সবচেয়ে বেশি দরকার, সেখানেই পৌঁছাত না।

### `GET /app/version`

```jsonc
{
  "versionCode": 3,          // ⚠️ সংখ্যা, স্ট্রিং নয়
  "versionName": "0.2.0",    // কেবল দেখানোর জন্য
  "url": "https://erp.adi.com.bd/app/abos-arm64.apk",
  "minimumCode": 1,
  "note": { "bn": "…", "en": "…" }   // ঐচ্ছিক, এক লাইন
}
```

⚠️ **`versionCode` সংখ্যা, আর সেটা এই কাগজের অন্য নিয়মটার ব্যতিক্রম নয় —
আলাদা প্রশ্ন।** §৩ নিয়ম গ বলে *টাকা* স্ট্রিং হিসেবে যায়, কারণ দশমিকের
নির্ভুলতা হারানো চলে না। এটা টাকা নয়, ক্রম — আর ক্রম স্ট্রিং হিসেবে তুলনা
করলে **`"0.2.0" > "0.10.0"` সত্যি হয়ে যায়**, যা মিথ্যা। তাই এখানে সংখ্যাই
ঠিক, আর উল্টোটা করলে ভুল হত।

⭐ **তুলনা হয় `versionCode` ধরে, নামের স্ট্রিং ধরে নয়** — Android নিজেও
তাই করে।

### দুইটা আলাদা প্রশ্ন, দুইটা আলাদা ঘর

| | মানে | ফোন কী করবে |
|---|---|---|
| `versionCode` > নিজেরটা | নতুন একটা আছে | **নরম নোটিশ** — সরিয়ে রাখা যায়, কাজ চলে |
| `minimumCode` > নিজেরটা | এই বিল্ড আর চলবে না | **শক্ত দেয়াল** — এগোনো যায় না |

⚠️ **দুইটা এক পতাকায় মেশানো যাবে না।** একটা সাধারণ আপডেট মানে "সুবিধা
হবে"; কিন্তু পেলোডের আকার বদলালে পুরনো বিল্ড **ফাঁকা নয়, ভুল** দেখাবে —
আর তখন ছেড়ে দেওয়া চলে না।

১২ সেপ্টেম্বরের ছয়টা বাগই তার প্রমাণ: অ্যাপ চলছিল, পর্দা আঁকছিল, প্রতিটা
সংখ্যা ভুল ছিল, আর কোনো পাহারা লাল হয়নি। **ওই অবস্থায় "চলতে দেওয়া"
সবচেয়ে খারাপ উত্তর।**

### ⛔ যে নিয়মগুলো ভাঙলে মাঠে ক্ষতি হবে

**ক · পরীক্ষা ব্যর্থ হলে কিছুই হবে না — নোটিশও নয়, দেয়ালও নয়।**

সবচেয়ে গুরুত্বপূর্ণ নিয়ম। সার্ভারে পৌঁছানো না গেলে ফোন **জানে না** সে
পুরনো কিনা, আর না-জানাকে "পুরনো" ধরে নিলে **নেট না থাকা প্রতিটা ফোন তালাবদ্ধ
হয়ে যেত** — অথচ নেট না থাকা অবস্থায় কাজ করাই এই অ্যাপের পুরো উদ্দেশ্য
(§০, মালিকের ১ নম্বর সিদ্ধান্ত)। একটা সংস্করণ-দেয়াল যা সংযোগ হারালে ওঠে,
সেটা অ্যাপটাকেই অকেজো করে দেয়।

**খ · অ্যাপ নিজে APK নামাবে না।** লিংকটা ব্রাউজারে খোলে। নিজে নামানো মানে
অ্যাপের ভেতরে একটা ইনস্টলার পথ, যা ভুল ফাইল বসানোর নতুন উপায় ছাড়া কিছু
দেয় না।

**গ · দেয়াল ওঠার আগে কিউ দেখাতে হবে।** ফোনে না-পাঠানো অর্ডার থাকলে দেয়ালটা
সেটা বলবে, নাহলে কেউ অ্যাপ মুছে নতুনটা বসিয়ে ফেলবেন আর সাথে অর্ডারগুলোও
যাবে। ⭐ ডকে (রিলিজের নিয়ম) একই কথা আছে: চাবি হারানো অসুবিধা, না-পাঠানো
অর্ডার টাকা।

**ঘ · `note` দুই ভাষায়** — `{bn, en}`। এক ভাষায় পাঠালে অন্য ভাষার ফোনে
অপঠিত লেখা বসত।

### ⓘ সার্ভারের দিকে একটা ছাড় লিখে রাখতে হবে

`EveryRouteIsGuardedTest` প্রতিটা রুটে `can:` খোঁজে। এই রুটটা ইচ্ছাকৃতভাবে
খোলা, তাই সেটা **কারণসহ ছাড়ের তালিকায়** থাকবে — নীরবে নয়। নাহলে পরের জন
ভাববেন ওটা ভুলে খোলা রয়ে গেছে, আর বন্ধ করে দেবেন।

## ৭ · হাজিরা · `sync/hr` · চাবি `hr.attendance.self`

**তারিখ:** ১৪ সেপ্টেম্বর ২০২৬। হ্যান্ডলারটা (`AttendanceSync`) আগে থেকেই ছিল
আর push নিত — অ্যাপে কেউ ছুঁত না। এই অংশটা সেটাই পড়ে লেখা, অনুমান করে নয়।

⭐ **এটাই একমাত্র পর্দা যা সব রোলের লাগে** — বিক্রয়কর্মী, গুদাম, ডিপো,
ডিস্ট্রিবিউশন, সবাই হাজিরা দেন। "একটাই অ্যাপ সবার জন্য" এখানে সবচেয়ে
সরাসরি।

### ⛔ মেনু থেকে আসবে না, আর সেটাই সবচেয়ে জরুরি কথা

```
মেনু সারি  hr.attendance.index  →  চাবি hr.attendance.view   (গোটা দলের)
Field Sales / Warehouse পায়     →  চাবি hr.attendance.self   (কেবল নিজের)
```

⚠️ **মাঠকর্মীর `/me` হাজিরার মেনু সারি কোনোদিন পাঠাবে না**, কারণ ওই সারির
চাবি তাঁর নেই। মেনু ধরে টাইল বানালে ফিচারটা **ঠিক তাঁদের কাছেই অদৃশ্য
থাকত যাঁদের জন্য এটা** — আর অফিসে বসা কেউ কোনোদিন ধরতে পারতেন না, কারণ
তাঁর পর্দায় ওটা দেখাত।

⭐ তাই এটা **synthetic টাইল** — `hr.attendance.self` অনুমতি থেকে সরাসরি,
ঠিক "নতুন অর্ডার" যেভাবে `sales.order.create` থেকে আসে।

*(দুইটা চাবি আলাদা রাখার কারণ হ্যান্ডলারেই লেখা: `view` দিলে একজন মাঠকর্মী
গোটা দলের হাজিরা দেখতেন — কে দেরি করেছে, কে ছুটিতে — আর সেটা সুবিধার
জন্য গোপনীয়তা বিক্রি করা হত।)*

### নামে — `GET /sync/hr/pull`

```jsonc
{
  "id": "01a0…",
  "workDate": "2026-09-14",
  "status": "present",        // present · absent · leave · holiday
  "inTime": "09:12",
  "outTime": null,
  "isLate": false,
  "remarks": null
}
```

ⓘ নিজের হাজিরাই কেবল ফেরে — `employee_id` ধরে, `user_id` থেকে পাওয়া।

### ওঠে — `POST /sync/hr/push`

```jsonc
{
  "workDate": "2026-09-14",   // ⚠️ বাধ্যতামূলক
  "status": "present",
  "inTime": "09:12",
  "isLate": false,
  "remarks": "…"              // ঐচ্ছিক
}
```

⛔ **`employeeId` পাঠাবেন না।** হ্যান্ডলার বলছে: পাঠালে সেটা নিজের হতে
হবে, নইলে **প্রত্যাখ্যান** — আর না পাঠালে নিজেরটাই ধরা হয়। ⭐ না পাঠানোই
নিরাপদ ও সঠিক; পাঠানো মানে একটা ভুল হওয়ার সুযোগ তৈরি করা যার কোনো লাভ নেই।

*(হ্যান্ডলারের মন্তব্য: অন্য কারো id পাঠালে চুপচাপ নিজেরটা বসিয়ে দেওয়া হয়
না। নীরব সংশোধন পরে "আমার হাজিরা কে দিল" প্রশ্নের জন্ম দিত।)*

### ⛔ যে নিয়মগুলো ভাঙলে নীরবে ভুল হবে

**ক · একই দিন দুইবার নয় — সার্ভার CONFLICT দেয়।** ওই দিনের সারি থাকলে
push প্রত্যাখ্যাত, কারণ অফিস হয়তো ইতিমধ্যে ছুটি বসিয়েছে আর একটা পুরনো
অফলাইন সারি সেটা চাপা দিত। ⚠️ **ফোনকেও একই দিন দুইবার কিউ করতে দেওয়া
যাবে না** — নাহলে সেলসম্যান দুইবার চাপবেন, দ্বিতীয়টা CONFLICT হয়ে ফিরবে,
আর তিনি ভাববেন হাজিরাটা হয়নি।

**খ · ঘড়িটা ফোনের, আর সেটা মেনে নেওয়া হয় চিহ্নসহ।** মাঠে আর কোনো ঘড়ি
নেই। কিন্তু ফোনের ঘড়ি বদলানো যায়, তাই সার্ভার দাবি-করা দিন আর পাওয়ার
দিনের ফাঁক দেখে একটা মন্তব্য জুড়ে দেয় (`synced_days_late`)। ⭐ **শাস্তি
নয়, চিহ্ন** — আর সেটা পর্দায় দেখা যায়, কলামে চাপা থাকে না। ⓘ অ্যাপ ওই
মন্তব্য মুছবে না বা লুকাবে না।

**গ · কেবল CREATE।** সংশোধন নেটওয়ার্কে, ওয়েব থেকে।

**ঘ · অফলাইনে লেখা যায় — মালিকের §০ সিদ্ধান্তের ব্যতিক্রম নয়, বাইরে।**
§০ বলে নেট ছাড়া কেবল **অর্ডার** — কথাটা বিক্রয়ের নথি নিয়ে, কারণ ওগুলো
নম্বর নেয়, মজুদ সরায়, খতিয়ানে বসে। হাজিরা ওই চারটার একটাও করে না: নম্বর
নেই, মজুদ নেই, দাম নেই, ক্রেডিট সীমা নেই। ⭐ আর স্পেক §৫.১০ সরাসরি
অফলাইন হাজিরা চায়, তাই হ্যান্ডলারটা `acceptsPush() === true`।

## ৮ · আজকের সংখ্যা · `GET /dashboard/today`

**তারিখ:** ১৬ সেপ্টেম্বর ২০২৬। মালিকের চাওয়া: *"বিক্রি · আদায় · নগদ, এক পাতায়।"*

⭐ ফোনে এটা ওয়েবের চেয়ে **ভালো** কাজ করে, আর কারণটা এই কাগজের বাকি সব
সিদ্ধান্তের মতোই সাধারণ: মালিক ডেস্কে বসে থাকলে ওয়েব খুলতেন। যে প্রশ্নটার
জন্য এই পর্দা — *আজ কেমন গেল* — সেটা তিনি জিজ্ঞেস করেন গাড়িতে, দোকানে, বা
রাতে।

### উত্তরের আকার

```jsonc
{
  "date": "2026-09-16",
  "company": "ADI",                 // কোন কোম্পানির সংখ্যা, ⚠️ দেখাতেই হবে
  "branch": "প্রধান শাখা",           // null হতে পারে — সব শাখা মিলিয়ে
  "asOf": "2026-09-16T18:04:11+06:00",

  "sales":       { "count": 12, "amount": "45200.0000" },
  "collections": { "count": 7,  "amount": "31000.0000" },
  "cashInHand":  { "amount": "18500.0000" },
  "dues":        { "amount": "812500.0000", "shops": 41 },
  "approvals":   { "pending": 3 }
}
```

⚠️ **টাকা স্ট্রিং, সংখ্যা গোনা int** — §৬-এর একই নিয়ম, একই কারণে: দশমিক
হারানো চলে না, আর ক্রম/গোনা স্ট্রিং হিসেবে তুলনা করলে ভুল হয়।

### ⛔ যে নিয়মগুলো ভাঙলে নীরবে ভুল হবে

**ক · অনুপস্থিত ঘর আর শূন্য এক জিনিস নয়।** যাঁর `accounts.till.view` নেই
তাঁর কাছে `cashInHand` **ঘরটাই যাবে না** — `null` বা `"0"` নয়। §৩ নিয়ম ঙ-এর
হুবহু একই নিয়ম, আর কারণও একই: শূন্য একটা সংখ্যা, যার উপর মানুষ সিদ্ধান্ত
নেন। "আজ নগদ শূন্য" আর "আপনি নগদ দেখতে পারেন না" — দুইটা আলাদা কথা।

**খ · কোন কোম্পানি, সেটা পর্দায় লেখা থাকবে।** একজন একাধিক কোম্পানিতে
থাকতে পারেন, আর অ্যাপে কোম্পানি বদলানোর পর্দা নেই (⚠️ জানা ফাঁক, ১৪
সেপ্টেম্বর)। সংখ্যাগুলো কার — সেটা না লিখলে ভুল কোম্পানির হিসাব দেখে
সিদ্ধান্ত নেওয়া হবে, আর কেউ বুঝবেই না।

**গ · "আজ" সার্ভারের দিন, ফোনের নয়।** ফোনের ঘড়ি বদলানো যায় (§৭ খ), আর
একটা ব্যবসায়িক দিন মধ্যরাতেই শেষ না-ও হতে পারে। তাই দিনটা সার্ভার ঠিক করে
আর `date` ঘরে বলে দেয়।

**ঘ · `asOf` দেখাতে হবে।** একটা বাসি সংখ্যা তাজা সংখ্যার মতোই দেখায়।
সংযোগ না থাকলে পর্দা **শেষবার পাওয়া সংখ্যাটাই** দেখাবে, সময়সহ — খালি
পর্দা নয়, আর তাজা বলে ভান করাও নয়।

**ঙ · অনলাইন-only, কিন্তু শেষ উত্তরটা ফোনে রাখা থাকে।** এটা সিঙ্কের অংশ
নয়, কিউ নেই, ওয়াটারমার্ক নেই — কিন্তু নেট ছাড়া খুললে "কিছু নেই" দেখানোর
চেয়ে "সকাল ১০টার হিসাব" দেখানো ভালো।

ⓘ **চাবি:** প্রতিটা ঘরের নিজের অনুমতি সার্ভারে ছাঁকা হবে — `sales.order.view`,
`sales.collection.view`, `accounts.till.view`, `customer.view`,
`approval.decide`। রুটে একটাও `can:` নয়, §০-এর শেষ নিয়ম অনুযায়ী।

## ৯ · রিপোর্ট · `GET /reports` ও `GET /reports/{key}`

**তারিখ:** ১৬ সেপ্টেম্বর ২০২৬। মালিক চেয়েছেন Finance · Accounts · Purchase ·
Inventory · Sales · System Administration — ছয়টা মডিউল ফোনে।

### ⭐ কেন ১০১টা চুক্তি নয়, দুইটা

ওই ছয় মডিউলে `/me` পাঠায় **১০১টা মেনু সারি**, আর তাদের আকার আশ্চর্যরকম
নিয়মিত:

```
.index (তালিকা)          ৫৫
report.show (slug ধরে)    ২৩
module.dashboard           ৬
একক কাজ                   ১৭
```

আর সার্ভারে **`ReportEngine` আগে থেকেই আছে** — রেজিস্ট্রি, `keys()`,
`run(key, filters, page, perPage)`, আর ফেরত আসে `ReportResult` (rows ·
totals · page · totalRows)। আজ **৩৩টা রিপোর্ট নিবন্ধিত**, প্রতিটার কলামে
ধরন ও অনুমতি বসানো।

⭐ অর্থাৎ **একটা দরজা দিয়েই তেত্রিশটা রিপোর্ট** যায় — আর ফোনে একটাই পর্দা
লাগে, কারণ কলামগুলো সার্ভার বলে দেয়।

### `GET /reports`

```jsonc
[ { "key": "sales.daily", "module": "sales", "title": "দৈনিক বিক্রয়",
```

⚠️ **কেবল সেগুলোই, যেগুলো এই ব্যক্তি চালাতে পারেন** — `ReportDefinition`-এর
`permission` ধরে ছাঁকা। ⓘ ফোন তালিকাটা এখান থেকেই বানায়, হাতে লেখা তালিকা
থেকে নয়; নতুন রিপোর্ট নিবন্ধিত হলে নতুন অ্যাপ রিলিজ ছাড়াই আসবে — ঠিক
`GET /sync/capabilities` যে কারণে আছে।

**ক · কলামগুলো সার্ভারের, আর `columnsFor($user)` দিয়ে ছাঁকা।** যে কলাম এই
ব্যক্তি দেখতে পারেন না, সেটা **উত্তরেই থাকবে না** — `null` বা ফাঁকা নয়।
⭐ এটা `purchasePrice`-এর নিয়মটারই সাধারণ রূপ (§৩ ঙ), আর ইঞ্জিনে ওটা আগে
থেকেই আছে। ফোন কলাম হার্ডকোড করবে না — করলে ৩৩টা রিপোর্টের জন্য ৩৩ বার
হার্ডকোড করতে হত, আর প্রতিটা সার্ভারের সাথে আলাদাভাবে বাসি হত।

**খ · ⛔ `totals` সার্ভারের, ফোন কখনো যোগ করবে না।** পাতা-ভাগ করা তালিকায়
দৃশ্যমান সারিগুলো যোগ করলে **১০০ সারির যোগফলকে "মোট" বলে দেখানো হত**, আর
৪১২ সারির রিপোর্টে সেটা নীরবে ভুল — সংখ্যাটা বিশ্বাসযোগ্য দেখাবে, কেবল
সত্যি হবে না। ⓘ `ReportResult` মোট আলাদা করে পাঠায় ঠিক এই কারণে।

**গ · টাকা ও পরিমাণ স্ট্রিং**, §৩ গ-এর মতোই। `type` দেখে ফোন সাজায়:
`money` → ৳ ও হাজারের কমা, `quantity` → দশমিক ছেঁটে, `date` → dd/MM/yyyy,
`document` → নম্বর, `percent` → %।

**ঘ · পাতা-ভাগ বাধ্যতামূলক।** একটা খতিয়ান পঞ্চাশ হাজার সারি হতে পারে, আর
সবটা একবারে পাঠানো মানে ফোনের মেমরি শেষ করা। ⚠️ `totalRows` আর `lastPage`
দুইটাই লাগবে — নাহলে পর্দা বলতে পারবে না "৪১২টার প্রথম ১০০টা দেখছেন", আর
মানুষ ভাববেন এটাই সব।

**ঙ · অচেনা `type` কাঁচা দেখাবে**, লুকাবে না। নতুন ধরন যোগ হলে পুরনো বিল্ড
সংখ্যাটা দেখাবে অন্তত — ফাঁকা ঘর নয়।

ⓘ **`.index`-এর ৫৫টা সারি এই চুক্তিতে নেই**, আর সেটা ইচ্ছাকৃত। ওগুলো CRUD
তালিকা, প্রতিটার নিজের আকার — আর ওগুলোর বেশিরভাগই ডেস্কের কাজ। যেগুলো
সত্যিই ফোনে দরকার (নথি দেখা), সেগুলো §১০-এর দরজা দিয়ে আসে।

## ১০ · নথি ও রপ্তানি · `GET /documents/…` ও `GET /reports/{slug}/export`

**তারিখ:** ১৯ সেপ্টেম্বর ২০২৬। মালিকের চাওয়া: *"মোবাইল অ্যাপ থেকে প্রিন্ট,
পস প্রিন্ট, রসিদ প্রিন্ট, শেয়ার PDF, এক্সেল যাতে করা যায়।"*

⚠️ **এই ধারাটা দেরিতে লেখা, আর সেটাই এর থাকার কারণ।** ফোনের দিকের কোড
(`lib/core/printing/documents_api.dart`) ১৬ সেপ্টেম্বর লেখা হয়েছিল, আর তার
মন্তব্যে লেখা ছিল "shape agreed … written into docs/Contract" — কিন্তু
লেখা ছিল না। অর্থাৎ ফোন তিনটা পথে ডাকছিল যেগুলো কোথাও সম্মত হয়নি। ১৯
সেপ্টেম্বর সার্ভারের কাজ ভাগ হওয়ার সময় ধরা পড়ল, বানানো শুরুর আগে। ⛔ দুই
পাশ আলাদা অনুমান থেকে বানানো — ১২ সেপ্টেম্বরের ছয়টা payload বাগ ঠিক এভাবেই
হয়েছিল, আর এক মাস সবুজ থেকে কিছুই আঁকেনি।

### কেন ইঞ্জিন নয়, দরজা

সার্ভারে `app/Core/Engines/Print` + mPDF আগে থেকেই আছে, আর ওয়েব ওটাই
ব্যবহার করে। ⭐ **একটাই বিন্যাস, একটাই মোট, একটাই জায়গা যেখানে ভ্যাটের
নিয়ম থাকে।** ফোনে কোনো নথি আঁকা হয় না, হবেও না — ফোন কেবল বাইট চায় আর
সেটা দেখায়, শেয়ার করে, বা তাপীয় প্রিন্টারে পাঠায়।

### `GET /documents/{type}/{id}/pdf?paper=a4`

উত্তর: **বাইট**, `Content-Type: application/pdf`।

```
paper   a4 · 80mm · 58mm          (PaperSize যা চেনে)
type    PurchaseBill · SalesInvoice · Payment · …
id      public_id, ক্রমিক id কখনো নয় (§৩ ক)
```

⚠️ **`type`-এর শব্দভাণ্ডার §৫-এর `documentType`-এর সাথে হুবহু এক** —
মডেলের ইংরেজি নাম, যেভাবে সার্ভার ফাইল করে। দুই জায়গায় দুই রকম নাম হলে
অনুমোদনের তালিকা থেকে নথি খোলা কাজ করত না, আর ভুলটা কেবল ঐ একটা ট্যাপে
ধরা পড়ত।

⓵ **`Content-Disposition`-এ আসল নামটা দিন** (`PB-2609-0007.pdf`), কারণ ফোন
ফাইলটা সেভ ও শেয়ার করে। প্রতিটা ফাইলের নাম `document.pdf` হলে শেয়ার-শিটে
সাতটা নথি আলাদা করা যায় না।

### `GET /documents/{type}/{id}/papers`

```jsonc
["a4", "80mm"]
```

⭐ **জিজ্ঞেস করা হয়, ধরে নেওয়া হয় না।** প্রতিটা টেমপ্লেটের তাপীয় সংস্করণ
নেই — ৫৮mm রোলে একটা খতিয়ান কেউ চায় না। ফোনে তালিকা হার্ডকোড করলে এমন
বোতাম দেখাত যেটা চেপে অর্থহীন কাগজ বেরোয়। ⓘ একই যুক্তি
`GET /sync/capabilities`-এর: সার্ভার জানে সে কী বানাতে পারে, তাই সে-ই বলে।

### `GET /reports/{slug}/export?format=xlsx&…`

উত্তর: **বাইট**। `format` — `csv` · `xlsx` · `json`, যে তিনটা `ListExport`
ইতিমধ্যেই বানায়। বাকি query ঘরগুলো §৯-এর `GET /reports/{key}`-এর ছাঁকনি,
হুবহু একই নামে।

⛔ **`docx` নেই**, মালিকের সিদ্ধান্ত ১৩ সেপ্টেম্বর: পাঠানোর নথি PDF,
সম্পাদনার সংখ্যা স্প্রেডশিট, আর তৃতীয় একটা রূপ মানে একই সংখ্যার তৃতীয়
একটা জায়গা যেখানে সে অন্য কথা বলবে।

⚠️ `{slug}` আর §৯-এর `{key}` **একই জিনিস** (`sales.daily`)। দুইটা আলাদা
শব্দ ব্যবহার করা হয়েছিল বলেই এখানে লেখা রইল — রিপোর্ট দেখা আর রপ্তানি
একই রিপোর্টকে দুই নামে চিনলে একদিন একটা কাজ করবে আর অন্যটা ৪০৪ দেবে।

### ⛔ যে নিয়মগুলো ভাঙলে নীরবে ভুল হবে

**ক · ⛔⛔ অনুমতি PDF-এর ভিতরেও খাটে।** এই পুরো চুক্তির সবচেয়ে বিপজ্জনক
দরজা এটাই। §৩ ঙ বলে `purchasePrice` ছাড়াই পণ্য যায়, §৯ ক বলে
`columnsFor($user)` কলাম ছেঁকে দেয় — কিন্তু **একটা PDF সার্ভারে আঁকা হয়,
আর সেখানে ঐ ছাঁকনি না বসালে ঠিক ঐ সংখ্যাগুলোই ছবি হয়ে ফোনে পৌঁছে যায়।**
যাঁর `inventory.cost.view` নেই তাঁর তোলা ক্রয় বিলের PDF-এ ক্রয়মূল্য
থাকবে না। ⚠️ আর ফাঁকটা নীরব: JSON-এ চাবি না থাকলে পর্দা কিছু আঁকে না, কিন্তু
PDF-এ সংখ্যাটা থাকলে সেটা দেখাই যায়, এবং কেউ টের পায় না যে সে দেখার কথা
ছিল না। ⓘ যাচাইটা দুই দিক থেকে, §৫-এর Payroll-এর মতোই: অনুমতিহীন ব্যক্তির
PDF-এ সংখ্যাটা **নেই**, আর অনুমতিওয়ালার PDF-এ **আছে**।

**খ · নথি দেখার অনুমতি নথিরই।** রুটে `can:` নয় (§০), ছাঁকনি হ্যান্ডলারে।
যে নথি এই ব্যক্তি দেখতে পারেন না, তার জন্য **403** — `404` নয়, কারণ ভিতরের
ব্যবহারকারীর কাছে "নেই" আর "আপনার নয়" দুইটা আলাদা কথা, আর প্রথমটা তাঁকে
খুঁজতে পাঠায়।

**গ · অচেনা `paper` চাইলে ৪২২, ভাঙা PDF নয়।** টেমপ্লেটে ৫৮mm না থাকলে
সার্ভার A4 দিয়ে "কাজ চালিয়ে" দেবে না — ফোন `papers` জিজ্ঞেস করেই নিয়েছে,
তাই এখানে অমিল মানে সত্যিকারের ভুল, আর সেটা চেপে যাওয়ার জিনিস নয়।

**ঘ · সংখ্যা সার্ভারে সাজানো।** `PrintEngine` যা লেখে ফোন তাই দেখায়;
ফোন PDF-এর ভিতরের কোনো অঙ্ক আবার সাজায় না বা যোগ করে না। §৯ খ-এর একই
কারণ — একই সংখ্যা দুই জায়গায় সাজালে একদিন দুই রকম দেখাবে।

**ঙ · এগুলো অনলাইন-only, কিউ নেই।** একটা নথি সেই মুহূর্তের অবস্থা; পুরনো
একটা PDF কিউ থেকে বেরিয়ে এসে বর্তমান বলে ভান করার চেয়ে "সংযোগ নেই" বলা
ভালো। §৫-এর অনুমোদনের মতোই।

**চ · বড় ফাইল।** একটা খতিয়ানের xlsx কয়েক MB হতে পারে। ফোন বাইটগুলো
অস্থায়ী ফাইলে নামায়, মেমরিতে ধরে রাখে না — কিন্তু সার্ভারের দিকেও পুরোটা
মেমরিতে বানিয়ে না পাঠানোই ভালো, একই কারণে।

ⓘ **ফোনের দিক তৈরি ও টেস্ট করা** — `documents_api.dart`,
`document_actions_sheet.dart`, আর `document_actions_test.dart`। দুইটা পথ
আছে: সিস্টেম প্রিন্ট/শেয়ার (যেকোনো প্রিন্টার, যেকোনো অ্যাপ) আর ব্লুটুথ
ESC/POS (রসিদ প্রিন্টার, সার্ভারের PDF রাস্টার করে)। আকার বদলাতে চাইলে
আগে এখানে বদলান, তারপর দুই পাশ — এই ধারাটা দেরিতে লেখা হওয়ার কারণটাই যেন
আবার না ঘটে।
