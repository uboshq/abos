## ৩. তিনটা সংশোধন — এবং কেন

এই তিনটাই একই ধরনের ভুল: **যে সমস্যা এখনো আসেনি, তার সমাধান আগে বানানো।**
তিনটাই দেখতে আধুনিক, তিনটাই কাগজে ঠিক, আর তিনটাই ডেলিভারি খেয়ে ফেলে।

### ৩.১ Metadata-driven **Field** — হ্যাঁ · Metadata-driven **Screen** — না (v1-এ)

**যা প্রস্তাবে আছে:** Form Designer, Layout Designer, Workflow Binding,
Calculated Fields — অর্থাৎ পর্দাগুলো ডাটাবেজের সংজ্ঞা থেকে তৈরি হবে।

**সমস্যা:** একটা Form Designer নিজেই একটা পণ্য। ওটা ঠিকমতো বানাতে গেলে দরকার
হয় লেআউট ইঞ্জিন, শর্তসাপেক্ষ দৃশ্যমানতা, ক্রস-ফিল্ড ভ্যালিডেশন, বাংলা/ইংরেজি
লেবেল, প্রিন্ট লেআউট, মোবাইল লেআউট, ভার্সনিং, আর ওই ডিজাইনারের নিজের একটা
UI। এই কাজটা শেষ হওয়ার আগে একটা ইনভয়েসও ছাপা যায় না। বাস্তবে যা হয়: টিম
ছয় মাস ডিজাইনার বানায়, তারপর সময় বাঁচাতে আসল স্ক্রিনগুলো হাতে লেখে — আর
ডিজাইনারটা পড়ে থাকে, কেউ ব্যবহার করে না।

**যা করতে হবে:**

- **Field-level metadata — এখনই।** প্রতিটা ঐচ্ছিক ফিল্ডের (VAT, Free Qty,
  Brand, Batch, Serial) একটা প্রতি-কোম্পানি সুইচ থাকবে, আর সুইচটা যোগ হবে
  ফিল্ডটার সাথেই — পরে নয়। ABOS-এ এটা ইতিমধ্যেই আছে: `module.php`-র
  `settings[]` → Control Panel।
- **Dynamic custom fields — Phase 2।** গ্রাহক নিজের বাড়তি ফিল্ড যোগ করতে
  পারবে (`entity_custom_fields` টেবিল + JSON মান)। এটা Form Designer নয়,
  এটা একটা তালিকা।
- **Form/Layout Designer — Phase 4-এর পরে, চাহিদা প্রমাণ হলে।** তিনজন আলাদা
  গ্রাহক একই জিনিস চাওয়ার আগে নয়।

> **পরীক্ষা:** কোনো ফিচারের জন্য যদি ডাটাবেজে একটা "কীভাবে দেখাতে হবে" সংজ্ঞা
> লিখতে হয়, আর সেই সংজ্ঞাটা লেখার জন্য কোনো UI নেই — তাহলে ওটা metadata নয়,
> ওটা লুকানো hard-code, শুধু ডিবাগ করা কঠিন।

### ৩.২ UUID **সবখানে নয়** — ভেতরে bigint, বাইরে UUIDv7

**যা প্রস্তাবে আছে:** "সব Entity UUID ভিত্তিক হবে।"

**সমস্যা:** MySQL 8 InnoDB-তে প্রাইমারি কী মানে ক্লাস্টার্ড ইনডেক্স। এলোমেলো
UUID প্রাইমারি কী দিলে প্রতিটা ইনসার্ট বি-ট্রির যেকোনো জায়গায় গিয়ে পড়ে, পেজ
ভাঙে, আর ইনডেক্স ২–৩ গুণ বড় হয়। প্রতিটা ফরেন কী ১৬ বাইট, প্রতিটা JOIN তত
ভারী। ABOS-এর ledger টেবিলে বছরে লক্ষ সারি বসবে আর রিপোর্টগুলো (trial balance,
ageing) সেগুলোর উপর GROUP BY করবে — ওখানেই দাম দিতে হবে। আর ডেপ্লয়মেন্ট
টার্গেট অফিসের ১৬GB Dell mini, ক্লাউড ক্লাস্টার নয়।

**যা করতে হবে:**

```
id           BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY   -- ভেতরের সব কিছু
public_id    CHAR(36) UNIQUE                              -- UUIDv7, API ও URL-এ
```

- ভেতরের FK, JOIN, রিপোর্ট — সব `id` দিয়ে।
- API, webhook, ইভেন্ট পেলোড, বাইরের ইন্টিগ্রেশন, ইমপোর্ট/এক্সপোর্ট — সব
  `public_id` দিয়ে। বাইরের কেউ কখনো `id` দেখবে না।
- UUIDv7 (এলোমেলো v4 নয়) — সময়-ক্রমানুসারী, তাই `public_id`-র ইউনিক
  ইনডেক্সও ভাঙে না।
- একটা `HasPublicId` trait, `booted()`-এ বসবে। এক জায়গা, সব মডেল।

এতে মাইগ্রেশনের স্বাধীনতাও থাকে: ভবিষ্যতে সত্যিই ডাটাবেজ ভাগ করতে হলে
`public_id` ইতিমধ্যেই বিশ্বব্যাপী অনন্য।

### ৩.৩ Modular Monolith — Microservices নয়, তবে Microservices-এর দিকে মুখ করে

**যা প্রস্তাবে আছে:** ১৪টা Platform + ৮টা Domain, "ভবিষ্যতের Microservices
Architecture", "Core Platform Services Stateless হবে এবং Horizontal Scaling
সমর্থন করবে"।

**সমস্তা:** ২২টা সার্ভিস মানে ২২টা ডেপ্লয়, ২২টা লগ, ২২টা মাইগ্রেশন চেইন, আর
প্রতিটা ক্রস-সার্ভিস কোয়েরির জন্য নেটওয়ার্ক। ডেপ্লয়মেন্ট টার্গেট একটা LAN
সার্ভার যেটা ইন্টারনেট না থাকলেও চলতে হবে। ওখানে microservices মানে খরচ সব,
লাভ কিছু নয়।

**যা করতে হবে:** এক Laravel অ্যাপ, কিন্তু **সীমানা কড়া** —

- প্রতিটা Domain নিজের ফোল্ডারে, নিজের `module.php` ম্যানিফেস্ট নিয়ে।
- এক Domain অন্য Domain-এর **মডেল সরাসরি ছোঁবে না** — Service বা Event।
- Core কখনো কোনো Domain-এর নাম লিখবে না (ABOS-এ এটা একটা টেস্ট দিয়ে পাহারা
  দেওয়া হয়)।
- একটা আর্কিটেকচার টেস্ট থাকবে যেটা ভাঙা সীমানা ধরবে (§৯.৪)।

সীমানা কড়া থাকলে ভবিষ্যতে যেকোনো Domain আলাদা করে বের করা যাবে। সীমানা ছাড়া
microservices বানালে সেটা distributed monolith — সবচেয়ে খারাপ জায়গা।

**ব্যতিক্রম — read:** রিপোর্টিং cross-domain JOIN করতে পারবে। Trial balance,
ageing, বকেয়া তালিকা — এগুলো SQL-এর কাজ, আর প্রতিটা সারির জন্য সার্ভিস ডাকলে
১০,০০০ কোয়েরি হত। **Write কখনো নয়, read সবসময়** — এটাই নিয়ম, আর
Reporting-কে আলাদা bounded context হিসেবে দেখা হবে।

## ৪. স্তরবিন্যাস

```
UBOS Platform
│
├── Core Platform Services      ← কোনো Domain-এর নাম জানে না
├── Identity & Security
├── Governance                  ← Policy, Audit, Compliance, Retention
├── Metadata                    ← Field-level (§৩.১)
├── Reference Data              ← Currency, Country, UOM, Tax …
├── Workflow                    ← Approval, SLA, Escalation
├── Integration                 ← REST, Webhook, Event Bus, Import/Export
├── Analytics                   ← Dashboard, KPI, Report Engine
├── Search
├── Document                    ← DMS engine
├── Notification
├── AI                          ← OCR, Extraction, Assistant
│
└── Business Domains
    ├── Sales      ├── Purchase   ├── Inventory
    ├── Finance    ├── HR         ├── CRM
    ├── Manufacturing             └── DMS
```

**অলঙ্ঘনীয়:** তীরের দিক সবসময় উপরে। Domain → Platform ডাকতে পারে;
Platform → Domain কখনো নয়। Platform কোডে কোনো Domain-এর ক্লাসনাম, টেবিলনাম বা
রুটনাম লেখা থাকলে সেটা রিভিউতে বাতিল।

## ৬. লুকানো Shared Data — মালিকানার ছক

এগুলোর কোনো UI মেনু নেই। সেটিংস/Control Panel থেকে সম্পাদনা হয়, আর সব Domain
পড়ে।

| ডেটা | মালিক | সম্পাদনা কোথায় | নিয়ম |
|------|-------|-----------------|------|
| Company · Branch · Business Unit | Core | System Management | প্রতিটা কোয়েরিতে scope |
| Currency · Exchange Rate | Reference Data | System Management | ইতিহাস রাখতে হবে |
| UOM · Conversion | Reference Data | Settings | ভগ্নাংশ অনুমোদিত কি না, ফিল্ড |
| Tax / VAT | Reference Data | Settings | হার বদলালে পুরনো ডকুমেন্ট বদলাবে না |
| Country › Division › Region › Area › Territory › Point › Route | Reference Data | Settings | **একটাই গাছ**, দুইটা নয় |
| Payment Terms | Reference Data | Settings | দেনা ও পাওনা দুই দিকেই |
| Party Type | Reference Data | Settings | সারি, enum নয় — কোম্পানি বাড়াতে পারবে |
| Number Series | Core | Settings | মডিউলের ঘোষণা থেকে তৈরি |
| Fiscal / Business Calendar | Core | System Management | ব্যাক-ডেট তালা এখান থেকে |
| Address · Contact | Core | inline | যেকোনো Entity-তে polymorphic |
| Tag · Comment · Attachment | Core | inline | polymorphic |
| Approval Matrix | Workflow | Governance | module থেকে ঘোষিত |
| Holiday · Timezone · Language | Core | System Management | — |

> নয়। দ্রুততা আসবে inline quick-create থেকে, দ্বিতীয় তালিকা থেকে নয়।

## ৭. Event-Driven — সীমা সহ

**একই প্রক্রিয়ায়, একই ট্রানজেকশনে যা ঘটতেই হবে** (হিসাবের দাখিলা, স্টক
চলাচল, নম্বর ইস্যু) — সেগুলো সরাসরি সার্ভিস কল, ইভেন্ট নয়। ইভেন্ট হারালে
খাতা মেলে না, আর "eventually consistent ledger" বলে কিছু নেই।

**ইভেন্ট শুধু পার্শ্বপ্রতিক্রিয়ার জন্য:** নোটিফিকেশন, সার্চ ইনডেক্স, ওয়েবহুক,
রিপোর্ট ক্যাশ, AI এক্সট্রাকশন, ইন্টিগ্রেশন।

```
InvoiceConfirmed  →  (sync)  PostingEngine, StockEngine, NumberSeries
                  →  (async) Notification, Search, Webhook, Analytics
```

ইভেন্টের নাম অতীত কালে (`InvoiceConfirmed`), পেলোডে `public_id`, আর
পেলোড **স্ব-সম্পূর্ণ** — গ্রাহক ইভেন্ট পেয়ে আবার ডাটাবেজে ফিরে আসবে না।

## ৯. উন্নয়নের নিয়ম

### ৯.১ প্রতিটা Entity-তে বাধ্যতামূলক

| # | নিয়ম | কেন |
|---|------|-----|
| ১ | প্রতিটা সংখ্যা তার উৎসে যেতে দেবে (`source_type` + `source_id`) | ক্লিক করে দেখা যাবে কোন ডকুমেন্ট থেকে এল |
| ২ | প্রতিটা কোয়েরিতে `company_id` scope | টেন্যান্ট বিচ্ছিন্নতা |
| ৩ | প্রতিটা রুটে permission | ফাঁকা রাখলে ধরা পড়ে না |
| ৪ | প্রতিটা ইনপুটে ভ্যালিডেশন | — |
| ৫ | মোছা নয়, নিষ্ক্রিয় করা — আর ফেরার পথ থাকবে | একমুখী দরজা মানে ডুপ্লিকেট রেকর্ড |

| ৯ | দুই ভাষা সবসময় (bn + en) | একটা থাকলে অন্যটা নীরবে fallback করে |

### ৯.২ Domain-এর `module.php` যা ঘোষণা করবে

```php
return [
    'code'          => 'purchase',
    'name'          => ['en' => 'Purchase', 'bn' => 'ক্রয়'],
    'depends_on'    => ['accounts', 'inventory', 'supplier'],
    'menu'          => [...],   // রুট না থাকলে সারি থাকবে না
    'permissions'   => [...],
    'doc_types'     => ['PO' => '...', 'GRN' => '...'],
    'drill_sources' => [...],   // নিয়ম ১
    'reports'       => [...],
    'settings'      => [...],   // নিয়ম ৭
    'events'        => [...],   // কী প্রকাশ করে
];
```

Core এই ফাইলটা পড়ে রুট, ভিউ, অনুবাদ, মাইগ্রেশন, মেনু, অনুমতি, নম্বর সিরিজ,
রিপোর্ট ও সেটিংস — সব নিবন্ধন করবে। **নতুন মডিউল যোগ করতে কোর কোডে একটা
লাইনও লিখতে হবে না।**

### ৯.৩ API-First

- প্রতিটা Domain-এর `Routes/api.php`, স্বয়ংক্রিয় `api/{domain}/…` উপসর্গ।
- সব `public_id` দিয়ে, `id` কখনো নয়।
- ভার্সন হেডারে (`Accept: application/vnd.ubos.v1+json`), URL-এ নয়।
- UI যা করতে পারে, API-ও পারবে — বিশেষ করে ইমপোর্ট, কারণ সেখানেই নিয়মগুলো
  সবচেয়ে বেশি ফাঁকি দেওয়া হয়। **তাই সব ব্যবসায়িক নিয়ম Service-এ, Controller
  বা FormRequest-এ নয়** — নাহলে ইমপোর্টে নিয়ম খাটে না।

### ৯.৪ আর্কিটেকচার টেস্ট (CI-তে বাধ্যতামূলক)

1. Core কোডে কোনো Domain-এর নাম নেই।
2. এক Domain অন্য Domain-এর Model import করে না।
3. প্রতিটা রুটে permission মিডলওয়্যার আছে।
4. প্রতিটা মডিউলের দুই ভাষার অনুবাদ ফাইল আছে, আর কী-গুলো মেলে।
5. ঘোষিত প্রতিটা মেনু রুট সত্যিই বিদ্যমান (দুই দিকেই)।
6. প্রতিটা `doc_type`-এর নম্বর সিরিজ তৈরি হয়।
7. টাকার হিসাবে `float` নেই — সব `bcmath` + `DECIMAL(18,4)`।

> এই টেস্টগুলো **রেজিস্ট্রি ধরে হাঁটবে**, হাতে লেখা তালিকা ধরে নয়। তালিকা ধরে
> লিখলে নতুন মডিউল যেদিন আসে সেদিন টেস্ট চুপ থাকে — অর্থাৎ ঠিক যখন দরকার তখন।

## ১৪. যে ফাঁদগুলোতে পড়া যাবে না

1. **No-Code Designer আগে বানানো।** §৩.১।
2. **"পরে ঠিক করব" মাস্টার ডেটা।** দ্বিতীয় গ্রাহক তালিকা একবার তৈরি হলে আর
   মেলানো যায় না।
3. **রিপোর্টের নিজস্ব হিসাব।** রিপোর্ট লেজার থেকে গুনবে, আলাদা কলাম থেকে নয়।
   দুই কপি একদিন আলাদা হবেই, আর তখন কোনটা সত্যি বলার উপায় থাকবে না।
4. **Controller-এ ব্যবসায়িক নিয়ম।** ইমপোর্ট ও API ওই পথে যায় না।
5. **enum দিয়ে "ধরনের তালিকা"।** প্রতিটা নতুন ধরনের জন্য একটা রিলিজ লাগত,
   আর ততদিন সবাই "অন্যান্য" লিখত।
6. **"কাজ করছে" মানে টেস্ট পাস।** লগইন বোতাম সাবমিট না করা, অদৃশ্য হেডিং,
   ৩ মিটার লম্বা রসিদ — একটাও টেস্টে ধরা পড়েনি, ব্রাউজারে চোখে দেখে ধরা
   পড়েছে। **বানাও, তারপর তাকাও।**
7. **হাতে লেখা তালিকা ধরে টেস্ট।** রেজিস্ট্রি ধরে হাঁটো।
8. **যেখানে খুঁজেছি সেখানে নেই মানে নেই।** একই দিনে দুইবার এই ভুল হয়েছে:
   `::name` ঠিক করতে গিয়ে ফাইলের সব `::` বদলে ফেলা (কম্পোনেন্ট ট্যাগে
   ওটাই সঠিক ছিল, ১৫টা কাজ করা পর্দা ভেঙেছিল), আর middleware-এ `can:`
   না দেখে "পাহারাহীন" ধরে নেওয়া (`ReportController` পদ্ধতির ভেতরেই
   `abort_unless` দিয়ে চাবি চায়)। **দুইবারই টেস্ট ধরিয়ে দিয়েছে যে
   নিয়মটা ভুল, কোড নয়।**

## ১৪.১ যা একবার দেখা গেছে — সারানো হয়নি, ইচ্ছাকৃতভাবে

**পুরো সুইটে একটা MySQL ডেডলক** (১২ আগস্ট ২০২৬)। ৯৫৮টা টেস্টের মধ্যে
একটায়, `DemoSeeder`-এর `branches` ঢোকানোর সময়:

```
SQLSTATE[40001]: Deadlock found when trying to get lock
insert into `branches` ... PurchaseTest::test_a_partial_bill_leaves_the_rest_pending
```

একা চালালে ৩৩/৩৩ পাশ। অর্থাৎ কোডের দোষ নয়।

**কেন সারানো হয়নি:** কারণটা জানা যায়নি, আর একবার দেখা যাওয়া জিনিসের
পেছনে অনুমান করে কোড বদলানো মানে কাজ করা প্রোডাকশন কোডে হাত দেওয়া।
`DB::transaction`-এ retry বসালে ভুলটা ঢাকা পড়ত, খুঁজে পাওয়ার পথও বন্ধ হত।

**যা জানা দরকার যদি আবার হয়:** এটা নতুন কিছু নয় — একবার দেখা গেছে, আর
এই লাইনগুলো তার প্রমাণ। **CI লাল হলে প্রথমেই ধরে নেবেন না বিল্ড ভাঙা**;
আগে দেখুন এররটা এই ডেডলকই কিনা, আর ওই টেস্টটা একা চালিয়ে দেখুন। দুই-তিনবার
হলে তখন এটা আসল সমস্যা, আর তখন কারণ খুঁজে সারাতে হবে — `RefreshDatabase`-এর
বাইরের লেনদেন আর `CompanyProvisioner`-এর ভেতরের লেনদেনের মিথস্ক্রিয়া
প্রথম যেখানে দেখতে হবে।

### ১৬.৩ "DMS" শব্দটা দুইটা আলাদা জিনিস বোঝায় — সাবধান

প্রথমে ভেবেছিলাম এখানে একটা দ্বৈততা আছে। নেই, কিন্তু যা আছে সেটা আরও
বিভ্রান্তিকর: **একই তিন অক্ষর দুইটা সম্পূর্ণ ভিন্ন জিনিসের নাম।**

| যেখানে লেখা | পুরো নাম | আসলে কী |
|-------------|----------|---------|
| এই প্ল্যানের Business Domains-এ | **D**ocument **M**anagement **S**ystem | ফাইল, ফোল্ডার, টেমপ্লেট, ভার্সন, আর্কাইভ |
| আলাদা পণ্য `ubos-dms` | **D**istribution **M**anagement **S**ystem | ডিপো/পরিবেশক ERP — Sales, Purchase, Inventory, POS, HR |

`ubos-dms`-এ ডকুমেন্ট ব্যবস্থাপনা বলে আলাদা কিছু নেই; ওখানে একটা
`core/document` ইঞ্জিন আছে, যা ওই ERP-র নিজের সংযুক্তির জন্য। অর্থাৎ
কোনো কাজ দুইবার হচ্ছে না।

**যা করতে হবে:** প্ল্যানে "DMS" নামটা ব্যবহার করা বন্ধ। Business
Domain-টার নাম হবে **Documents**, আর `ubos-dms` বোঝাতে সবসময় পুরো
নাম বা রেপোর নাম। নাহলে ছয় মাস পর কেউ "DMS ধাপে হাত দাও" শুনে ভুল
পণ্যে কাজ শুরু করবে — আর সেটা টের পাওয়া যাবে অনেক দেরিতে।

> এটাই একমাত্র জায়গা নয় যেখানে নাম বিভ্রান্তি তৈরি করে। চারটা পণ্য
> (`ubos-dms`, `adi`, `ubos`, `dbosERP`) আলাদা ও চালু — একটার নাম
> অন্যটার সংক্ষিপ্ত রূপের মতো শোনালেই সেগুলো এক জিনিস নয়।

### ১৬.৪ যা এখনো জানা নেই — পরিমাণের অনুমান
