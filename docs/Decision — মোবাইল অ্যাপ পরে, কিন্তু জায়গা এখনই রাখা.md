# সিদ্ধান্ত — মোবাইল অ্যাপ পরে, কিন্তু জায়গাটা এখনই রাখা

**তারিখ:** ১ সেপ্টেম্বর ২০২৬
**মালিকের কথা:** *"ERP কমপ্লিট হলে অ্যাপ বানাবো, সেই ব্যবস্থা করে রাখতে হবে।"*

---

## আজ কী আছে — মাপা, অনুমান নয়

```
api রুট                 ০
Sanctum / Passport      ০
JSON ফেরত দেয়           ২টা কন্ট্রোলার
mobile ফোল্ডার          নেই
```

**ABOS-এর কোনো API স্তর নেই।** পুরোটাই সার্ভার-রেন্ডার করা Blade।

---

## তাই সবচেয়ে জরুরি কথাটা

**অ্যাপ বানানোর খরচের ৮০% ফ্রেমওয়ার্ক নয়, API।** যেকোনো নেটিভ অ্যাপের
আগে প্রতিটা পর্দার জন্য একটা API লাগবে, টোকেন-অথেন্টিকেশন লাগবে, আর
মাঠে নেট না থাকলে অফলাইন সিঙ্ক লাগবে — শেষেরটাই সবচেয়ে কঠিন।

**ফ্রেমওয়ার্ক বাছাটা বাকি ২০%**, আর সেটা তখন বাছলেই চলবে।

---

## "জায়গা রেখে দেওয়া" বলতে ঠিক কী

অস্পষ্ট প্রস্তুতির কোনো মানে নেই। **আজকের কোড লেখার সময় তিনটা নিয়ম
মানলেই** পরে অ্যাপের কাজটা কয়েক সপ্তাহ ছোট হয়ে যায়:

### ১ · ব্যবসার নিয়ম কন্ট্রোলারে নয়, সার্ভিসে

ABOS **এটা এখনই ভালো করে** — `SalesInvoiceService`, `PostingEngine`,
`DirectSaleService`। কন্ট্রোলার কেবল যাচাই করে আর ডাকে।

**নিয়মটা রাখতে হবে:** নতুন কোনো ব্যবসার নিয়ম যেন কন্ট্রোলার বা Blade-এ
না বসে। বসলে অ্যাপের দিন ওই নিয়মটা **দ্বিতীয়বার** লিখতে হবে, আর তখন
দুইটা আলাদা উত্তর দেবে।

*পরীক্ষা:* একটা সার্ভিস কি HTTP ছাড়া, কেবল PHP থেকে ডাকা যায়?
`abos:books-check` কমান্ডটা ঠিক এভাবেই কাজ করে — ওটাই প্রমাণ।

### ২ · প্রতিটা ডকুমেন্টের বাইরের পরিচয় থাকতে হবে

`public_id` (UUID) প্রতিটা টেবিলে আছে, আর `PublicIdTest` পাহারা দেয়।

**কেন লাগে:** অ্যাপ অফলাইনে একটা বিল বানাবে, তখন সার্ভারের `id` জানা
থাকবে না। নিজের UUID নিয়ে এসে সিঙ্ক করলে **একই বিল দুইবার বসে না** —
আর ঠিক এই কারণেই POS-এ `idempotency_key` বসানো হয়েছে
(`uq_pos_sale_idempotency`)।

**নিয়মটা রাখতে হবে:** নতুন টেবিলে `publicId()` ম্যাক্রো, আর যা বাইরে
থেকে তৈরি হতে পারে তাতে একটা idempotency চাবি।

### ৩ · একই কাজ দুইবার এলে একবারই ঘটবে

আজ এটা তিন জায়গায় আছে: POS-এর `idempotency_key`, খতিয়ানের
`posted_documents` প্রহরী-টেবিল, আর নম্বর সিরিজের row lock।

**কেন লাগে:** মোবাইল নেটওয়ার্কে অনুরোধ দুইবার যাওয়া নিয়ম, ব্যতিক্রম নয়।
এটা না থাকলে অফলাইন সিঙ্ক **নিশ্চিতভাবে** হিসাব দ্বিগুণ করত।

## যখন সময় হবে — দুইটা পথ, দুই রকম দাম

| | কী | দাম |
|---|---|---|
| **ক** | **PWA** — এখনকার পর্দাগুলো ফোনে ভালো করে তোলা, হোম স্ক্রিনে বসে | **~৩ দিন** |
| **খ** | **নেটিভ অ্যাপ** — API + টোকেন + অফলাইন সিঙ্ক | **~২৫–৩৫ দিন**, তারপর চিরকাল দুইটা কোডবেস |

**(ক) যথেষ্ট যদি** চাওয়াটা হয় "একই পর্দা ফোনে দেখব"।
**(খ) লাগবে যদি** মাঠের বিক্রয়কর্মী নেট ছাড়া কাজ করবেন।

**(খ) হলে Flutter** — কারিগরি কারণে নয়, ব্যবহারিক: HP মেশিনে Flutter
টুলচেইন ইতিমধ্যেই বসানো, আর প্রতিষ্ঠানের অন্য মোবাইল কাজও Flutter।
তৃতীয় একটা স্ট্যাক আনার কোনো কারণ নেই।

**অর্থাৎ সিঙ্ক এমনভাবে লিখতে হবে যাতে সে থেমে থেমে চলতে পারে**, একটানা
নয়। পরে ভাবলে পুরোটা আবার লিখতে হত।

## যোগ · ২ সেপ্টেম্বর ২০২৬ — "NEXUS-এর অ্যাপটা কি ABOS-এ কাজে লাগানো যাবে?"

মালিকের প্রশ্ন। উত্তরটা মেপে দেওয়া হলো, অনুমানে নয়।

### NEXUS-এর অ্যাপটা কী

```
mobile/lib/         ১৬৩টা Dart ফাইল
  core/              ৮৫  ← ব্যবস্থাপনা
  বাকি               ৭৮  ← পর্দা ও ব্যবসার ফিচার
সার্ভারের সাথে কথা   ১১৯টা ফাইল, ৬৬টা আলাদা endpoint
ঠিকানা               <host>/api/v1  (Java/Spring)
```

### উত্তর: **হ্যাঁ, অর্ধেকটা — আর ঠিক কঠিন অর্ধেকটাই**

`core/`-এর ভেতরে যেগুলো কোনো ব্যবসার নিয়ম জানে না, সেগুলো **যেকোনো
ERP-তে হুবহু খাটে**:

| অংশ | ফাইল | কেন এটাই দামি |
|---|---|---|
| `sync_engine` | ৭ (১,১৩২ লাইন) | **অফলাইন সিঙ্ক — অ্যাপের সবচেয়ে কঠিন জিনিস** |
| `design_system` | ১৮ | রং, মাপ, উপাদান |
| `auth` + `security` + `storage` + `device` | ১৫ | টোকেন, ডিভাইস আইডি, নিরাপদ সঞ্চয় |
| `i18n` + `theme` | ৩ | বাংলা/ইংরেজি, রূপ |
| `api_client` + `update` + `notifications` + `widgets` + `analytics` | ২০ | বাকি ব্যবস্থাপনা |

**মোট ~৬৩টা ফাইল** — এগুলোয় "বিক্রয়" বা "মজুদ" শব্দটাই নেই।

### যেটা কাজে লাগবে না, আর কেন

**১১৯টা ফাইল ৬৬টা Java endpoint-এর সাথে বাঁধা।** ABOS-এ `api` রুট
**শূন্য**, Sanctum **শূন্য** — অর্থাৎ ওই ১১৯টা ফাইল ABOS-এ কিছু খুঁজে
পাবে না।

### তাই আসল হিসাবটা উল্টে যায়

এই কাগজের উপরের অংশে লেখা আছে — *"অ্যাপ বানানোর খরচের ৮০% ফ্রেমওয়ার্ক
নয়, API"*। NEXUS-এর অ্যাপটা থাকায় **সেই ৮০%-এর ভেতরের সবচেয়ে কঠিন
টুকরোটা (অফলাইন সিঙ্ক) ইতিমধ্যেই লেখা ও চলমান**।

অর্থাৎ কাজটা আর "একটা অ্যাপ বানাও" নয়, **"ABOS-এ একটা API বানাও যেটা
NEXUS-এর `/api/v1`-এর মতো আকারের"** — আর তারপর অ্যাপের দিকে কেবল
`baseUrl` আর ওই ১১৯টা ফাইলের ভেতরের ম্যাপিং।

আগের হিসাব ছিল **~২৫–৩৫ দিন**। এই পথে **~১২–১৮ দিন**, আর তার
প্রায় পুরোটাই ABOS-এর দিকে (API + টোকেন), অ্যাপের দিকে নয়।

### তিনটা শর্ত — এগুলো না মানলে সুবিধাটা নেই

**১ · `mobile/` NEXUS-এর মোবাইল টিমের।** ওটা কপি করা নয়, **ভাগ করে
নেওয়া**। কোন অংশ সাধারণ আর কোন অংশ NEXUS-এর — সেই সীমাটা আগে ঠিক
করতে হবে, নাহলে দুই পণ্যের একটাতে বদল অন্যটাকে ভাঙবে।

**২ · Java-র API-র আকার হুবহু নকল করা যাবে না।** NEXUS-এর DTO ও
অনুমতির নাম তার নিজের ডাটা মডেল থেকে এসেছে। ABOS-এ সেগুলো জোর করে
বসালে **ABOS-এর মডেলটাই বিকৃত হবে** — আর সেটা ঠিক ওই "ভবিষ্যতে সমস্যা
হয় এমন কাজ"।

  ভাগ করে নেওয়ার জিনিস **প্রোটোকল**, DTO নয়: পাতা-ভাগ, ত্রুটির আকার,
  টোকেন নবায়ন, idempotency চাবি, সিঙ্কের কার্সার।

**৩ · কাজটা আজ শুরু করার নয়।** মালিকের নিজের কথা — *"ERP কমপ্লিট
হলে অ্যাপ বানাবো।"* এই কাগজের তিনটা নিয়ম (সার্ভিসে ব্যবসার নিয়ম ·
প্রতিটা টেবিলে `public_id` · একই কাজ দুইবার এলে একবার) মানতে থাকলে
সেদিন কাজটা ছোট থাকবে।

**যা আজ বদলাল:** কোন ফ্রেমওয়ার্ক — প্রশ্নটা আর খোলা নেই। **Flutter**,
কারণ শুধু টুলচেইন নয়, **একটা চলন্ত সিঙ্ক ইঞ্জিন** ওদিকে ইতিমধ্যেই আছে।
